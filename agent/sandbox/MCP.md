# Nutz OpenTTD MCP Server

Connect any AI agent that speaks [Model Context Protocol](https://modelcontextprotocol.io)
to a running OpenTTD server. The MCP server exposes the live game state plus
read/write tools so the agent can observe and act.

## What an agent can do

- **Read** game state: companies, vehicles, stations, towns, year, money, perf
- **Dispatch** a bus route blueprint (intra-town or pair) — the in-game Nutz Executor
  AI then builds the stations, road, depot, and bus
- **Send chat** messages broadcast to all players
- **Pause / unpause** the game
- **Run** raw rcon commands

## Prerequisites

- Python 3.9+ (`admin_client.py` is stdlib only)
- OpenTTD 15.x running locally with admin port enabled (default `:3977`)
- Nutz Bridge game script loaded in the game (auto-loads on heightmap scenarios
  generated by `agent/sandbox/build_scenario.py`)
- For dispatching routes: the Nutz Executor AI must be running in-game

## Install for Claude Desktop

Edit `~/Library/Application Support/Claude/claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "openttd": {
      "command": "python3",
      "args": ["/full/path/to/agent-openttd-arena/agent/sandbox/mcp_server.py"]
    }
  }
}
```

Restart Claude Desktop. You'll see the OpenTTD tools appear in the chat input.

## Install for Cursor

`~/.cursor/mcp.json` (same shape). Or via Cursor Settings → MCP → Add Server.

## Install for Zed

Zed's settings:
```json
{
  "context_servers": {
    "openttd": {
      "command": {
        "path": "python3",
        "args": ["/full/path/to/agent-openttd-arena/agent/sandbox/mcp_server.py"]
      }
    }
  }

```

## Tools exposed

| Tool | Purpose |
|---|---|
| `game_state` | One-shot snapshot. Always call first. |
| `list_companies` | Companies with value, cargo, perf, name |
| `list_towns` | Top towns by population (limit param) |
| `list_vehicles` | Profit_ty, profit_ly, age per vehicle |
| `list_stations` | Stations with id, name, tile |
| `dispatch_route` | Plan + dispatch blueprint. Same town for from + to → intra-town mode |
| `send_chat` | Broadcast in OpenTTD chat |
| `pause` / `unpause` | Game control |
| `fund_town` | Advisory (in-game AI required to actually fund) |
| `rcon` | Raw console command — escape hatch |

## Try it

After connecting your agent, ask things like:
- *"What's the game state right now?"*
- *"List the top 5 towns by population."*
- *"Dispatch an intra-town route in the biggest town."*
- *"Which buses are losing money?"*
- *"Pause the game and tell everyone hello."*

The agent reads game state, decides what to do, calls the tool, and reports
back. Compose its own strategy on top — e.g. "monitor every minute, dispatch
new routes when the company has > $100k cash."

## How it works

```
Your agent  ──MCP/stdio──>  mcp_server.py  ──admin TCP──>  OpenTTD :3977
                                  │
                                  └── plans routes via planner.py
```

The MCP server is a thin tool-dispatch layer over `admin_client.py` (~280
lines, stdlib-only). The OpenTTD admin protocol is well-documented and
stable; we re-export it through MCP semantics so any tool-using LLM can drive
the game without learning OpenTTD's binary protocol.

## Limitations

- Read state via the bridge_gs game script (must be loaded; comes free with
  scenarios built by `build_scenario.py`)
- Dispatch routes requires the Nutz Executor AI running in-game (`start_ai
  "Nutz Executor"` via console)
- `fund_town` is advisory — in-game AI scripts can call `PerformTownAction`,
  but external tooling cannot directly modify another company's state. The
  workaround is to run the Nutz Executor and let its idle `GrowAllTowns`
  loop fund towns over time.
- All tool calls go through the same single admin connection; high-frequency
  polling can stress the OpenTTD admin protocol — keep call rates reasonable.
